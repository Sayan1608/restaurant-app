## Commands

PostgreSQL must be running for the backend **and for the backend tests** (see "Tests hit a real database" below).

```powershell
# Database (repo root) — publishes Postgres on host port 5433
docker compose up -d postgres

# Backend (from backend/)
.\mvnw.cmd spring-boot:run                      # dev server on :8080
$env:SPRING_PROFILES_ACTIVE="development"       # opt-in sample restaurant/menu seed
.\mvnw.cmd test
.\mvnw.cmd test -Dtest=OrderCheckoutControllerTests
.\mvnw.cmd test -Dtest=OrderCheckoutControllerTests#methodName

# Frontend (from frontend/) — npm is the chosen package manager
npm run dev
npm run lint
npx tsc --noEmit
npm run test                                    # vitest run
npm run test -- src/app/checkout-form.test.tsx
npm run build
```

Health: <http://localhost:8080/actuator/health>. OpenAPI: <http://localhost:8080/swagger-ui.html>. UI: <http://localhost:3000>.

Configuration comes from the **root `.env`**, which Spring Boot imports server-side (`spring.config.import` in `application.properties`) and Compose uses for substitution. The root `.env` may already hold a real `OPENROUTER_API_KEY` — never overwrite it when copying `.env.example`; add only missing keys. `frontend/.env.local` holds `NEXT_PUBLIC_API_BASE_URL` only.

## Architecture

Modular monolith: Spring Boot 3.5 / Java 21 backend (`backend/`, base package `com.restaurantapp`), Next.js 16 App Router frontend (`frontend/`), one PostgreSQL database. Backend packages are feature-sliced, not layer-sliced — `auth`, `user`, `restaurant`, `menu`, `orders`, `chat`, plus `common` (error shape) and `config` (security, dev seeder). DTOs are records living beside their controller/service; JPA entities never cross the HTTP boundary. IDs are `UUID` throughout.

### Session auth, not JWT

Browser auth is a Spring Session cookie (`HttpOnly`, `SameSite=Lax`, secure via `APP_SESSION_COOKIE_SECURE`) plus CSRF stored in the session (`HttpSessionCsrfTokenRepository`). Every mutating frontend call therefore does `GET /api/auth/csrf` first and sends the returned header/token — that pattern is already centralized in `frontend/src/lib/api.ts`; follow it rather than writing bare `fetch`. CORS allows exactly one credentialed origin (`APP_CORS_ALLOWED_ORIGIN`). Authorization is an explicit allowlist in `config/SecurityConfiguration.java` ending in `.anyRequest().denyAll()` — a new endpoint is unreachable until a matcher is added there. Ownership checks that security rules can't express (customer sees only their own order) live in `OrderService`.

### Order invariants live in OrderService

`OrderService.create` re-reads menu items from the database, rejects inactive/unavailable/duplicate/invalid lines, computes `subtotal`/`total` in `BigDecimal` (delivery fee and tax are deliberately `0.00` for now), and writes the order plus immutable `item_name`/`unit_price` snapshots in one transaction. The client sends only item IDs and quantities. Checkout is idempotent per customer via an `Idempotency-Key` header (UUID) stored on the order; replaying with changed details is rejected. Status transitions are enforced in `isAllowedTransition`: `PLACED → CONFIRMED → PREPARING → READY → COMPLETED`, with `CANCELLED` reachable only from `PLACED` or `CONFIRMED`. The same invariants are mirrored as SQL `CHECK` constraints in `V1__create_initial_schema.sql` (including `total = subtotal + delivery_fee + tax` and `line_total = unit_price_snapshot * quantity`) — a Java-side pricing change that breaks them fails at insert time, so change both together via a new migration.

### Chat assistant

`chat/` calls OpenRouter server-side only, with a dedicated `RestClient` bean (3s connect / 15s read timeout), a 2000-char reply cap, a 20 req/min in-memory per-client limiter, and a safe "unavailable" reply on provider failure. Context is built from `MenuService`'s current public menu — never order, customer, or credential data. The call is outside any transaction. Tests mock the client; nothing in CI may require a live key.

### Schema changes

Flyway is the source of truth (`backend/src/main/resources/db/migration/`, currently `V1`–`V3`); Hibernate runs with `ddl-auto=validate`, so an entity change without a matching migration fails startup. Add a new `V<n>__*.sql`; never edit an applied one.

### Frontend shape

`src/app/page.tsx` is a thin server component rendering `storefront.tsx`, a client component that owns menu, cart (persisted to `localStorage` under `restaurant-cart-v1`), auth modal, and chat state, and delegates to `checkout-form.tsx` and `order-center.tsx` (customer history + admin order desk) through injected callbacks — which is what makes those two unit-testable. All request/response types and every endpoint call are in `src/lib/api.ts`. Cart totals are a display estimate; the backend total is authoritative.

## Tests hit a real database

There is no `src/test/resources` and no Testcontainers dependency. `@SpringBootTest @ActiveProfiles("test")` tests run against the datasource from the root `.env` — i.e. the Compose Postgres on 5433. Start it before `mvnw.cmd test`, and if a test run can't reach it, report that as an environment limitation rather than weakening the test. Backend tests are `@Transactional` MockMvc integration tests using `SecurityMockMvcRequestPostProcessors.user(...)`/`csrf()` and `@MockitoSpyBean` for rollback simulation; name them `*Tests`. Frontend tests are Vitest + jsdom + Testing Library, co-located as `src/app/<component>.test.tsx`.

## Money and locale

INR, `BigDecimal` with scale 2 server-side; the frontend formats with `Intl.NumberFormat("en-IN")`. Timestamps are `Instant`.
